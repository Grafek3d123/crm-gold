# ТЗ №6 — Проверка состояния CRM и реализация первого MVP

**Репозиторий:** https://github.com/Grafek3d123/crm-gold

## Цель

Проверить фактическое состояние рабочей копии CRM, сохранить существующую работу, устранить архитектурные блокеры и реализовать первый работающий вертикальный срез CRM.

Не предполагать, что локальная рабочая копия совпадает с GitHub `main`. Не создавать второй Laravel-проект поверх существующей работы.

## Этап 1. Инвентаризация

До любых изменений проверить:

* `git status --short --branch`;
* `git log --oneline --decorate -10`;
* `git ls-files`;
* `git status --ignored --short`;
* наличие `composer.json`, `composer.lock`, `artisan`, `app/`, `routes/`, `database/`, `resources/`, `tests/`, `package.json` и frontend lock-файла;
* доступность PHP 8.3, Composer и Node/npm;
* наличие незакоммиченных и игнорируемых файлов;
* наличие документов требований и ADR.

Не выводить содержимое `.env` и других файлов с секретами.

Если Laravel-код уже существует, продолжить работу с ним. Если код отсутствует, сначала исправить архитектурные блокеры и только затем создать локальную основу приложения.

## Этап 2. Исправление архитектуры

Обновить `docs/ARCHITECTURE_FINAL.md` и соответствующие ADR.

Обязательно согласовать следующие решения.

### 1. Сопоставление клиентов

* Нормализовать телефон и email.
* Проверять оба контакта до окончательного сопоставления.
* Если телефон относится к Customer A, а email — к Customer B, не объединять клиентов автоматически.
* Не переносить конфликтующие контакты в чужую карточку.
* Сохранять исходные контактные данные обращения и создавать запись для ручной проверки.
* Не выполнять автоматический merge по Yandex ClientID, yclid или client_key.
* Ручное объединение разрешить только администратору, в транзакции и с сохранением истории.

### 2. Ручные обращения и сайты

* Для ручного обращения `site_id` может быть `NULL`.
* Для web API сайт определяется по проверенным серверным credentials.
* API одного сайта не может создавать обращения от имени другого.
* Тип источника обращения должен определяться явно.

### 3. Деньги, возвраты и прибыль

* Единый денежный тип — `NUMERIC(12,2)` согласно ADR-004.
* Не использовать `float` или `double` для денежных значений.
* Суммы платежей и возвратов хранить положительными; тип операции определяет, является ли запись оплатой или возвратом.
* Чистая оплаченная выручка рассчитывается как подтверждённые оплаты минус подтверждённые возвраты.
* Не учитывать возврат дважды.
* Разделять чистую оплаченную выручку, фактические расходы и фактическую прибыль.
* Не считать прибыль подтверждённой до выполнения заказа и фиксации фактических расходов.

Финансовые таблицы в этом этапе не создавать. Закрепить правила документально для будущего финансового этапа.

### 4. Договоры и заказы

* Установить одну каноническую связь: `orders.contract_id`.
* Не создавать конкурирующую встречную связь без подтверждённой необходимости.
* Описать `contract_versions` или `contract_revisions`.
* Подписанная версия договора неизменяема; исправление создаёт новую версию.
* На данном этапе договоры и заказы не реализовывать.

### 5. Другие решения

* Для Blade/Livewire использовать Laravel session authentication и CSRF; Sanctum не должен становиться обязательным вторым механизмом входа.
* Не связывать анонимные события с Customer только по ClientID или yclid.
* Не придумывать API рекламного приложения.
* Уточнить недостающие поля `activities`, если они необходимы бизнес-процессам.
* Согласовать область первого MVP: публичные endpoints заказов и платежей в неё не входят.

В разделе Open Questions оставить только действительно нерешённые вопросы.

Для каждого вопроса указать:

* Question;
* Why it matters;
* Recommended default.

## Этап 3. Реализация первого вертикального среза

После исправления архитектурных блокеров реализовать только перечисленные ниже функции.

### Стек

* PHP 8.3;
* Laravel 13;
* PostgreSQL;
* Blade;
* Livewire 3;
* Alpine.js;
* Tailwind CSS;
* Vite.

Не добавлять React/Vue, Docker, Horizon или Repository pattern без отдельного обоснования. Не обходить ошибки совместимости зависимостей через `--ignore-platform-reqs`.

### Authentication и RBAC

Реализовать:

* login/logout;
* безопасную работу сессии и CSRF;
* роли `admin` и `manager`;
* серверные Policies/Gates;
* ограничение частоты попыток входа;
* безопасное создание первого администратора без фиксированного пароля в исходниках.

Менеджер не должен иметь административных прав.

### Customers

Реализовать:

* `customers`;
* `customer_identities`;
* нормализацию контактов;
* безопасный алгоритм сопоставления;
* ручное объединение клиентов только администратором;
* audit trail объединения и сохранение attribution history.

### Inquiries

Реализовать входящие обращения для web-форм и ручной регистрации звонков.

Предусмотреть:

* Customer;
* сайт и тип источника;
* исходные контактные данные;
* текст обращения;
* UTM-поля;
* landing и referrer;
* ClientID и yclid;
* внешнюю идентификацию;
* историю статусов;
* timestamps в UTC.

Статусы первого этапа:

`new`, `qualified`, `converted`, `rejected`, `duplicate`, `archived`.

Переходы контролировать через enum и явную state transition логику.

### Публичный API

Реализовать только:

* `POST /api/v1/inquiries`;
* `POST /api/v1/events`.

Требования:

* отдельные credentials для каждого сайта;
* HMAC-SHA256;
* timestamp window ±300 секунд;
* проверка подписи по точным исходным байтам HTTP body;
* constant-time сравнение подписи;
* rate limiting;
* серверная проверка scope сайта;
* idempotency для повторных запросов;
* отказ при недействительных credentials и подписи;
* защита секретов от попадания в frontend, Git, логи и ответы API.

Не реализовывать API заказов, платежей и `/conversions`.

### Attribution, audit и outbox

Реализовать:

* `marketing_events`;
* `touchpoints`;
* `audit_logs`;
* внутреннюю запись `conversion_events`/outbox для поддерживаемых событий.

Создание обращения, истории статуса, touchpoint, audit и связанных outbox-записей выполнять атомарно в рамках соответствующей бизнес-операции.

Не отправлять реальные запросы рекламному приложению, пока не подтверждены URL, credentials и контракт интеграции.

### CRM UI

Реализовать защищённые экраны:

* login;
* список и карточка клиентов;
* список и просмотр обращений;
* создание ручного обращения;
* изменение статуса обращения.

Проверки прав должны работать на сервере, а не только скрывать кнопки в интерфейсе.

## Этап 4. Тесты и проверка результата

Написать и фактически запустить тесты на:

* нормализацию phone/email;
* сопоставление и конфликт идентичности клиентов;
* запрет автоматического merge по ClientID/yclid;
* переходы статусов;
* успешную и неуспешную HMAC-проверку;
* просроченный timestamp;
* изоляцию credentials между сайтами;
* повторные idempotency keys;
* атомарность inquiry, status history, audit и outbox;
* разграничение прав admin/manager;
* доступ к CRM без авторизации.

Ключевые проверки целостности выполнять на PostgreSQL. Не подменять недоступные PostgreSQL-тесты успешным прогоном на SQLite.

В отчёте указать реальные команды, результаты и причины блокировок. Выполнить frontend build, если окружение это позволяет.

## Git и безопасность

* Сохранить все исходные пользовательские изменения.
* Изменения выполнять в feature branch, если это безопасно для текущего состояния.
* Не делать force-push и не отправлять изменения напрямую в `main`.
* Перед коммитом проверить diff на наличие секретов, `.env`, PII, `vendor/`, `node_modules/` и production dumps.
* Если push доступен, опубликовать feature branch и сообщить подтверждённый commit SHA.
* Если push невозможен, сохранить результат локально и указать причину.

## Итоговый отчёт

Обязательно указать:

1. Исходную ветку, commit и состояние Git.
2. Был ли Laravel-код в рабочей копии до начала работ.
3. Какие архитектурные блокеры исправлены.
4. Какие исходники и документы изменены или созданы.
5. Какие тесты действительно пройдены и какие заблокированы.
6. Результат frontend build.
7. Итоговую ветку, commit SHA и статус публикации.
8. Все невыполненные пункты.
9. Подтверждение, что production и SWeb не изменялись.

## STOP CONDITION

После завершения первого вертикального среза и итогового отчёта остановиться.

Не начинать договоры, версии договоров, заказы, расходы, платежи, возвраты, загрузку файлов, реальную отправку рекламных конверсий, CI/CD и deploy.

Не заявлять о готовности CRM к эксплуатации, пока соответствующие тесты и проверки не выполнены фактически.

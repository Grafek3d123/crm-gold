# ТЗ №5 — Поэтапная реализация MVP CRM

**Проект:** CRM `crm.zoloto-spb.ru`  
**Этап:** первый вертикальный срез MVP — инженерная база, авторизация, клиенты, входящие обращения и защищённый API  
**Основа:** `docs/ARCHITECTURE_FINAL.md` (rev.2) после устранения указанных ниже противоречий  
**Режим выполнения:** локальная разработка в Git-репозитории; production/SWeb полностью вне области работ  
**Главное правило:** реализовать только этот этап, проверить его тестами, зафиксировать результат и остановиться. Не переходить автоматически к заказам, договорам, платежам и интеграциям.

---

## 0. Цель задания

Перейти от архитектурной документации к работающей, проверяемой основе CRM. В результате этапа должна существовать локально запускаемая Laravel CRM, в которой:

1. менеджер или администратор может войти в CRM;
2. роли и права проверяются на сервере;
3. можно просматривать и редактировать карточки клиентов;
4. можно регистрировать входящие обращения вручную;
5. два внешних сайта могут передавать обращения и маркетинговые события через `/api/v1`;
6. запросы API проходят HMAC-проверку, ограничение частоты и idempotency;
7. повторная заявка не создаёт второго клиента, если совпадает нормализованный телефон или email и нет конфликта;
8. обращения и attribution history сохраняются атомарно;
9. критичные изменения фиксируются в `audit_logs`;
10. событие для будущей передачи в рекламное приложение записывается в transactional outbox, но внешняя отправка не включается без подтверждённого webhook-контракта;
11. автоматические тесты подтверждают критичные сценарии.

Этот этап **не является реализацией всей CRM**. Его задача — создать надёжный, протестированный вертикальный срез, на котором последовательно строятся остальные доменные процессы.

## 3. Архитектурные несостыковки, которые необходимо закрыть до миграций

До создания миграций и реализации соответствующей логики внести согласованные правки в `docs/ARCHITECTURE_FINAL.md` либо оформить отдельные ADR, на которые этот документ ссылается. Не оставлять разработчику выбор между несколькими противоречащими трактовками.

### 3.1 Customer matching

Текущая формулировка «первое совпадение побеждает» противоречит сценарию, где телефон соответствует Customer A, а email — Customer B. Алгоритм должен сначала найти совпадения **по обоим** контактам, а затем применить правило решения:

- совпали только телефон или только email — использовать соответствующего клиента;
- оба поля совпали с одним Customer — использовать его;
- телефон совпал с A, а email с B — не объединять A и B; не переносить конфликтующее значение email в карточку A; сохранить данные входящего обращения, отметить конфликт для ручной проверки и записать audit/activity;
- внешние ID, ClientID, yclid и cookie/session key не являются достаточным основанием для автоматического объединения людей.

Уникальные индексы на нормализованные телефон/email должны согласовываться с этим алгоритмом и учитывать только активные, не объединённые карточки. Обработать конкурентное создание Customer через транзакцию и повторное сопоставление после unique-violation.

### 3.2 Manual inquiries и site

В архитектуре `inquiries.site_id` объявлен обязательным, но входящий звонок, зарегистрированный менеджером, может не иметь сайта. Согласовать схему одним способом:

- `site_id` допускает `NULL` для ручных обращений;
- `source_kind` явно различает, например, `web_form`, `call`, `email`, `other`;
- machine API не может создать обращение с произвольным `site_id`: источник выводится из проверенных API credentials;
- для веб-обращения `site_id` обязателен и должен соответствовать credential сайта.

### 3.3 Деньги и финансовые события

ADR-004 фиксирует `NUMERIC(12,2)`, тогда как поля договоров, заказов, расходов и позиций используют `NUMERIC(14,2)`. Для этого этапа принять единый стандарт **`NUMERIC(12,2)` для денежных значений во всех таблицах**; никакого `float`/`double` в расчётах и persistence. Если владелец бизнеса позже подтвердит необходимость большей суммы, изменить точность отдельным ADR до миграций финансовых таблиц.

В архитектуре отдельно определить:

- подтверждённые платежи — единственный источник фактически полученных денег для revenue/conversion;
- возвраты не должны увеличивать выручку: зафиксировать единое правило расчёта net paid revenue (подтверждённые входящие платежи минус подтверждённые возвраты) и связь возврата с исходным платежом;
- договорная прибыль и денежные поступления — разные метрики; не вычислять прибыль как сумму платежей автоматически;
- агрегаты `sum_paid`, `sum_expenses`, first/last attribution и подобные поля, если они кэшируются, должны быть явно обозначены как projections, иметь механизм пересчёта и не становиться вторым источником истины.

Договоры, заказы, платежи и расходы в этом этапе не реализовывать; указанные решения должны быть записаны для следующих этапов.

### 3.4 Contract/order relationship and versioning

В схеме одновременно указаны `contracts.order_id` и `orders.contract_id`, что создаёт две конкурирующие связи. До этапа реализации договоров зафиксировать одну каноническую связь. Рекомендуемый вариант: `orders.contract_id` — единственная ссылка заказа на договор; не добавлять обратный FK без подтверждённого требования.

ADR утверждает хранение старых редакций договора, но описание таблиц не определяет законченный механизм версионирования. До реализации договоров описать `contract_versions` и версионирование компонентов суммы, файлов и статусов. Не перезаписывать подписанную редакцию договора.

Статус договора `paid` также неоднозначен при нескольких частичных платежах. Рекомендуемый вариант: статус договора описывает жизненный цикл документа (`draft/sent/signed/rejected/cancelled`), а `unpaid/partially_paid/paid` рассчитывается отдельно из подтверждённых платежей и суммы актуальной подписанной версии. Зафиксировать решение в ADR до реализации финансового этапа.

### 3.5 Order state machine and profit

Согласовать переходы заказа так, чтобы `completed` достигался только из `delivered`, если бизнес-владелец не утвердит исключение. Не разрешать отмену завершённого заказа обычным переходом.

В документе расходятся формулы `actual_profit = sum_contract - actual expenses` и `profit = revenue - actual_cost`. Для следующего финансового этапа закрепить раздельные показатели:

- `net_paid_revenue` — подтверждённые поступления минус подтверждённые возвраты;
- `actual_cost` — подтверждённые фактические расходы мастерской; материалы клиента исключаются;
- `actual_profit` — согласованная финальная цена продажи минус фактические расходы после завершения заказа и подтверждения всех расходов;
- все оценочные значения в интерфейсе маркируются как estimates и не передаются как факт конверсии.

Если бизнес ожидает денежный результат по реально полученным деньгам, это отдельный показатель и не подменяет `actual_profit`.

### 3.6 Activities and attribution identities

В требованиях к активности упомянуты `direction` (`in/out`), автор и время события, но таблица `activities` не содержит явного поля `direction` и в ней не описано, какое время считается временем события. Согласовать поля до миграции и не прятать обязательные доменные свойства неявно в JSON.

Архитектура говорит о первой идентифицированной посещённой странице по `client_key`, но не определяет устойчивую связь `client_key` с Customer. На первом этапе не связывать анонимные события с человеком только по ClientID/yclid. Создавать touchpoint для достоверно связанного обращения; правила склейки анонимной истории зафиксировать отдельно до включения promotion для анонимных visits.

### 3.7 Livewire and Sanctum

Для Blade + Livewire UI использовать обычную Laravel session authentication и штатную CSRF-защиту. Не считать Sanctum обязательным механизмом входа для Livewire. Не создавать SPA-токены без действительного потребителя. Если Sanctum уже установлен и предусмотрен для отдельного machine/SPA API, сохранить его только для конкретной подтверждённой задачи; не вводить второй конкурирующий механизм пользовательской сессии.

Перед использованием Livewire 3 проверить фактические ограничения Composer и запустить smoke-тест на используемой версии Laravel 13. Не обходить несовместимые constraint-ы через `--ignore-platform-reqs`.

### 3.8 Files/security — только документировать на этом этапе

`files` упоминается в связях, но не имеет полного описания схемы и модели доступа. До реализации загрузки файлов подготовить ADR/схему для private storage, размера и MIME allowlist, безопасного имени и случайного storage key, авторизации скачивания, запрета прямой публичной выдачи, журналирования загрузки/скачивания и обработки удалений/замены. Реализацию файлов отложить до отдельного этапа.

## 4. Решения по открытым вопросам на этот этап

Использовать следующие значения по умолчанию без повторного вопроса владельцу, если в локальных требованиях нет более конкретного подтверждённого решения:

1. **Внешняя запись Orders/Payments:** первично ручная регистрация в CRM; публичные API endpoints Orders/Payments не реализовывать в этом этапе. Их контракты согласовать перед будущим этапом интеграции.
2. **Рекламное приложение:** реальный URL webhook, credentials и payload contract не предоставлены в доступной архитектурной документации. Реализовать устойчивую запись outbox и тестируемый HTTP client boundary, но не включать реальную внешнюю доставку и не придумывать endpoint.
3. **Валюта:** в MVP только RUB; валютное поле сохраняется явно. Не выполнять FX-конвертацию.
4. **Retention marketing_events:** 180 дней с плановой очисткой; touchpoints и финансовая история не удаляются по этому retention правилу. Месячное партиционирование не вводить без подтверждённого объёма и измерений.
5. **SMTP:** локальные feature tests используют fake mail transport. Не пытаться отправлять реальные письма в тестах; production SMTP не конфигурировать.

Не блокировать текущую реализацию из-за отсутствия рекламного webhook, SMTP или внешней системы Orders/Payments. Эти интеграции должны быть безопасно отключены до предоставления контрактов и секретов.

## 5. Технические рамки

- PHP 8.3; Laravel 13; PostgreSQL.
- Blade + Livewire 3 + Alpine.js + Tailwind CSS + Vite.
- Не добавлять React/Vue.
- Не использовать Docker как обязательное условие разработки или production.
- Не добавлять Repository pattern без доказанной необходимости.
- Бизнес-операции размещать в явных Actions/use cases; Controllers остаются тонкими.
- Не создавать generic `CrmService`, `CustomerService` или другие god objects.
- Время сохранять в UTC в `TIMESTAMPTZ`; отображение дат — в согласованной timezone приложения.
- Любые секреты, `.env`, реальные данные клиентов, production connection strings и токены запрещены в Git.
- Не использовать SQLite как замену PostgreSQL в тестах критичных индексов и matching.

## 6. Реализуемый объём первого этапа

### 6.1 Project baseline

- воспроизводимая установка зависимостей через `composer.lock` и frontend lock file;
- `.env.example` с placeholders без секретов;
- инструкции для локального запуска и тестирования;
- безопасные Laravel configuration defaults для production, без выполнения deploy;
- базовые команды тестов и frontend build;
- если уместно, минимальный health route, не раскрывающий конфигурацию, secrets или сведения об инфраструктуре.

### 6.2 Authentication and RBAC

- login/logout;
- безопасное хеширование пароля;
- защита от session fixation: регенерация сессии при входе;
- проверка `is_active` при аутентификации и авторизации;
- роли `admin`, `manager`;
- Policies/Gates на стороне сервера для каждой изменяющей операции;
- ограничение частоты попыток входа;
- экран/механизм создания первого администратора без фиксированного пароля в исходниках и seeders;
- пароль reset/email flow — реализовать каркас только в рамках того, что можно локально протестировать; фактический SMTP не настраивать.

Менеджер не может управлять пользователями и системными настройками. Ручное слияние клиентов доступно только `admin` на первом этапе.

### 6.3 Reference data

- `sites`: `us812.ru` и `zoloto-spb.ru`;
- `sources`: нормализованные source codes; неизвестный `utm_source` не должен молча превращаться в выдуманную известную кампанию;
- seeders должны быть повторно запускаемыми (idempotent) и не создавать дубликаты.

### 6.4 Customers and identities

Реализовать:

- `customers` с нормализованными `phone` и `email` и исходными значениями, если они нужны для корректного отображения;
- `customer_identities` для внешних идентификаторов;
- Customer matching по правилам из §3.1;
- ручное слияние только администратором, в одной транзакции, с переносом поддерживаемых связей, сохранением merge audit и без потери attribution history;
- исключение объединённой карточки из обычного поиска и matching;
- запрет автоматического merge по ClientID, yclid или `client_key`.

Если внешняя identity конфликтует с уже связанной карточкой, не перезаписывать связь безусловно: оставить исходные значения события/обращения, зафиксировать конфликт и не потерять историю.

### 6.5 Inquiries and statuses

Реализовать модель входящего обращения `inquiries` — веб-форма или вручную зарегистрированный звонок — с:

- Customer;
- source kind и при необходимости site;
- исходными контактными значениями;
- текстом обращения;
- status backed enum и явной state machine;
- историей переходов `inquiry_status_history` (append-only);
- UTM-полями, landing, referrer, Yandex ClientID, yclid;
- `external_id` от сайта с областью уникальности, согласованной с `site_id`;
- timestamps UTC и минимально необходимыми техническими metadata;
- валидацией длины/формата данных на границе API;
- невозможностью менять статус в обход state machine.

Разрешённые статусы на данном этапе: `new`, `qualified`, `converted`, `rejected`, `duplicate`, `archived`. Недопустимые переходы должны возвращать контролируемую доменную ошибку. История статусов и audit log не soft-delete.

### 6.6 Marketing events and touchpoints

Реализовать раздельные сущности:

- `marketing_events` — технические события сайта;
- `touchpoints` — бизнес/attribution history, не перезаписывающаяся при новом обращении.

На первом этапе поддержать регистрацию web inquiry, базовых маркетинговых событий, UTM (пять стандартных полей плюс raw metadata) и touchpoint на достоверно зарегистрированное обращение. Не строить платформу аналитики событий. Не превращать автоматически каждую page view в touchpoint.

Реализовать projection first/last touch только после появления проверяемой записи touchpoint; должна быть команда/сервис пересчёта из истории. Не использовать Customer fields как единственное хранилище attribution.

### 6.7 Public machine API

Реализовать только endpoints:

- `POST /api/v1/inquiries`;
- `POST /api/v1/events`.

Публичные `POST /api/v1/orders`, `POST /api/v1/payments` и любой `/conversions` endpoint не включать в этом этапе.

Для каждого сайта — отдельный API key/secret, определяемый на server side. Секрет не может попасть в JavaScript, Blade output, клиентский bundle, Git или логи.

#### HMAC contract

Использовать единую подпись:

```text
HMAC_SHA256(
  api_secret,
  UPPERCASE_METHOD + "\n" +
  PATH_WITHOUT_QUERY + "\n" +
  TIMESTAMP_HEADER_AS_SENT + "\n" +
  LOWERCASE_HEX_SHA256_OF_EXACT_RAW_BODY_BYTES
)
```

Фиксировать алгоритм однозначно для клиента и сервера. Не пересериализовывать JSON перед проверкой подписи: хешируется точное тело HTTP-запроса. Сравнивать подписи constant-time способом. Допустимое окно timestamp — ±300 секунд. Проверять active credential и scope сайта. При неправильной подписи, просроченной метке или неверном scope — fail closed.

Создать документ `docs/API_CONTRACT.md` с заголовками, алгоритмом подписи, примером payload, успешными и ошибочными HTTP-ответами и воспроизводимыми test vectors для обеих сторон. Никакие реальные secrets в примерах не использовать.

#### Idempotency

Для создания inquiry ключ обязателен: `Idempotency-Key` либо поддерживаемый `external_id` в соответствии с единым контрактом. Область ключа включает site credential и operation.

- повтор того же ключа с тем же hash возвращает исходный cached response и не дублирует inquiry/customer/touchpoint/outbox;
- тот же ключ с другим request hash возвращает `422` с машинно-читаемым error code;
- сохранение idempotency result и бизнес-записи должно быть атомарным;
- конкурентные одинаковые запросы не должны создавать дубли;
- retention idempotency записей по умолчанию — 30 дней, после истечения запись может очищаться плановой задачей;
- `/api/v1/events` дедуплицируется по отдельному event key и не создаёт дублей в пределах принятого срока хранения.

Добавить конфигурируемое rate limit на credential, изначальный default — 60 запросов в минуту, без предположения, что это окончательная бизнес-квота.

### 6.8 Atomicity, audit and outbox

Создание обращения должно быть одной транзакцией:

1. проверить/создать Customer;
2. создать Inquiry;
3. записать touchpoint;
4. записать первую запись `inquiry_status_history`;
5. записать `audit_logs`;
6. записать `business_events` для `inquiry_received` (если этот тип события предусмотрен исправленной схемой);
7. сохранить ответ idempotency.

Никакого HTTP-запроса к рекламному приложению или другой внешней системе внутри транзакции. Outbox создаётся вместе с бизнес-операцией; доставка отделена от её коммита.

Для этого этапа outbox можно надёжно записывать и тестировать, но реальная внешняя отправка должна оставаться выключенной, пока нет подтверждённого URL, схемы и способа авторизации рекламного приложения. При отсутствии конфигурации job не должна отправлять запрос на догаданный адрес; событие должно остаться доступным для обработки, а причина недоставки — диагностируемой без утечки secrets.

### 6.9 CRM UI

Минимальный UI на Blade/Livewire:

- `/login`;
- `/dashboard` с минимальными счётчиками обращений и клиентов;
- `/customers` и `/customers/{id}`;
- `/inquiries` и `/inquiries/{id}`;
- форма ручного создания обращения, включая входящий звонок;
- на карточке клиента/обращения — связанные контакты и attribution history, где она имеется;
- базовая фиксация заметок/активностей, необходимых для отметки конфликта matching;
- состояния загрузки, валидации, пустого списка и ошибок;
- пагинация, серверная фильтрация, безопасное экранирование пользовательского текста.

Все изменяющие действия Livewire должны авторизоваться серверно. Blade visibility checks не заменяют Policies/Gates. Не делать UI для договоров, заказов, расходов, платежей, файлов и advanced analytics в этом этапе.

## 8. Database and privacy

- PostgreSQL — основная БД и БД интеграционных тестов.
- Все foreign keys имеют согласованную стратегию удаления/ограничений.
- Нормализованные phone/email и все поля поиска имеют обоснованные индексы.
- Все timestamps хранятся в UTC.
- Не сохранять raw IP без обоснованной необходимости; использовать предусмотренный privacy подход с salted hash.
- Ограничивать User-Agent и metadata; валидировать размер JSON payload.
- Не логировать тела запросов, содержащие лишние персональные данные, secrets, подписи, пароли или API keys.
- Не хранить незапрошенные данные из произвольных JSON keys; принимать только схему разрешённых полей.
- `orders`, `payments`, `audit_logs` и status histories в будущем не должны использовать soft delete. На первом этапе status histories и audit logs являются append-only.
- Не запускать миграции на production и не использовать production connection string в тестовой конфигурации.

## 9. Тесты — обязательный критерий приёмки

### Unit tests

- нормализация телефона и email;
- matching: phone-only, email-only, phone+email на одного клиента;
- конфликт phone→Customer A и email→Customer B без автоматического merge и без перезаписи контакта;
- ClientID/yclid не являются основаниями автоматического matching;
- разрешённые и запрещённые переходы Inquiry status;
- HMAC canonical string и проверка подписи;
- построение first/last attribution projections.

### Feature tests

- вход/выход и блокировка неактивного пользователя;
- роли admin/manager и прямой запрос к запрещённой операции;
- валидный HMAC-запрос создаёт ровно один Customer (или использует существующего), Inquiry, history, touchpoint, audit и outbox;
- неправильная подпись, stale timestamp, неактивный API key и несовпадение сайта отклоняются;
- повтор того же Idempotency-Key возвращает исходный результат без дублей;
- повтор с другим payload и тем же ключом возвращает `422`;
- конкурентная повторная отправка не создаёт дублей, насколько это воспроизводимо в тестовой БД;
- API не принимает `site_id` другого сайта из тела запроса;
- ручное обращение типа `call` допустимо без сайта;
- `/api/v1/events` сохраняет разрешённую схему события и дедуплицирует event key;
- payload с неизвестными/избыточными полями не сохраняется целиком;
- при rollback транзакции не остаются частичные Inquiry/Touchpoint/Audit/Outbox записи.

### Integration/environment tests

- реальные migrations выполняются на PostgreSQL test DB;
- partial unique indexes работают на PostgreSQL;
- внешняя доставка рекламному приложению в тестах подменена fake HTTP;
- `npm run build` завершается успешно, если frontend toolchain входит в проект;
- smoke test страницы входа, Customers и Inquiries не выдаёт 500.

Если локальной PostgreSQL нет, не подменять её молча SQLite: подготовить тесты и явно зафиксировать инфраструктурный блокер. Не объявлять все тесты успешными, если часть не запущена.

## 10. Разрешённые действия и строгие запреты

### Разрешено

## 11. Порядок выполнения и stop conditions

1. Выполнить §1 и записать `docs/IMPLEMENTATION_BASELINE.md`.
2. Выполнить архитектурные уточнения §3 в `docs/ARCHITECTURE_FINAL.md` и `docs/IMPLEMENTATION_DECISIONS.md`. Не удалять прежние ADR бесследно: изменение объяснить, сохранить историю решения.
3. Проверить и зафиксировать локальный Laravel baseline.
4. Реализовать только объём §6.
5. Добавить и выполнить тесты из §9; проверить миграции на PostgreSQL.
6. Проверить `git diff`, отсутствие secrets, локальных `.env`, vendor/build artifacts (если они должны быть исключены) и непредусмотренных файлов.
7. Подготовить отчёт о выполнении.
8. **Остановиться.** Не начинать следующий этап даже если кажется, что он очевиден.

Если обнаружен блокер, который меняет доменную модель, безопасность, source-of-truth финансовых данных или протокол HMAC, остановиться на соответствующей части, подробно описать проблему, её последствия и рекомендуемый вариант. Не маскировать блокер временным упрощением.

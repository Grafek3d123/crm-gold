# ТЗ №7 — Восстановление фронтенда CRM после переноса на новый шаблон

**Проект:** `crm-gold`  
**Репозиторий:** https://github.com/Grafek3d123/crm-gold  
**Приоритет:** P0 — frontend regression  
**Режим:** сначала диагностика, затем точечное исправление. Не переписывать приложение целиком.

## 1. Симптомы и цель

После переноса/подключения нового frontend-шаблона CRM:

- кнопки перестали работать или перестали выполнять ожидаемые действия;
- вёрстка сместилась, элементы перекрывают друг друга или потеряли прежние размеры/отступы;
- возможны проблемы с меню, формами, модальными окнами, таблицами и адаптивностью.

Задача — установить первопричины регрессии и восстановить работоспособность интерфейса с новым визуальным шаблоном. Внешний вид сам по себе не считается восстановленным, если кнопки и формы не выполняют реальные действия.

**Не считать причину заранее известной.** Проверить JS/Livewire/Alpine, подключение Vite-ассетов, CSS-конфликты, HTML-разметку, события кнопок и браузерные ошибки. Не ограничиваться изменением z-index, отступов или добавлением глобальных обработчиков.

## 2. Обязательная инвентаризация — до изменения файлов

1. Зафиксировать `pwd`, имя ветки и текущий commit:
   ```bash
   git status --short --branch
   git log --oneline --decorate -10
   git diff --stat
   git diff --name-status
   git status --ignored --short
   ```
2. Определить фактический корень Laravel-проекта. Проверить наличие `artisan`, `composer.json`, `composer.lock`, `package.json`, lock-файла npm, `vite.config.*`, `resources/css`, `resources/js`, `resources/views`, `public/build/manifest.json`, `routes/` и `tests/`.
3. Установить, в каком коммите и каких файлах был подключён новый шаблон. Сравнить изменения с последней рабочей версией через `git diff <предыдущий_рабочий_commit>...HEAD` (после определения правильного commit; не угадывать его).
4. Сохранить пользовательские изменения. Не запускать `git reset --hard`, `git clean -fd`, массовое удаление файлов и автоматическое форматирование всего проекта.
5. Не читать и не выводить содержимое `.env`, ключей, токенов, cookies, production-логинов и секретов.

**Особенность репозитория:** при внешней проверке GitHub корневые `package.json` и `composer.json` не обнаружены (raw URL возвращали 404). Это не доказывает, что локального приложения нет: оно может находиться в другом каталоге/ветке или ещё не быть опубликовано. Найди фактическую рабочую копию. Если исходников приложения нет ни в рабочей папке, ни в отслеживаемых файлах, не генерируй новое приложение ради выполнения этого ТЗ — остановись и сообщи, где именно отсутствует код.

## 3. Жёсткие ограничения

- Не изменять SWeb и production.
- Не делать deploy и не запускать миграции.
- Не менять `.env` и production credentials.
- Не менять бизнес-логику, модели, схему БД и API, если это не доказанная непосредственная причина регрессии. Если для исправления требуется backend-изменение, сначала зафиксировать доказательство и свести изменение к минимуму.
- Не удалять Livewire/Alpine, Tailwind, Vite или новый шаблон без доказанного конфликта.
- Не обновлять весь набор npm/Composer dependencies и не менять lock-файлы просто «на всякий случай».
- Не добавлять новые функции и не заниматься рефакторингом, не связанным с восстановлением фронтенда.
- Не коммитить и не пушить напрямую в `main`; работать в отдельной feature-ветке либо оставить локальные изменения, если ветку создавать небезопасно.

## 4. Диагностика технических причин

### 4.1 Vite и статика

Проверить:

- соответствуют ли `@vite([...])` в Blade фактическим entry points в `vite.config.*`;
- существуют ли CSS/JS файлы в `resources/` и попадают ли они в manifest;
- нет ли смешения старых ссылок на `public/css`, `public/js`, CDN и новых Vite-сборок;
- нет ли оставшегося `public/hot`, из-за которого приложение продолжает ссылаться на локальный Vite dev server;
- нет ли запросов CSS/JS с HTTP 404/403, неверным MIME type или ошибками CSP;
- правильны ли base path и пути к шрифтам, иконкам, изображениям и background assets;
- не загружается ли одновременно старый и новый комплект ассетов.

Не удалять `public/hot` вслепую: сначала определить, используется ли локальный dev server; производственные исправления не выполнять. Сборку запускать локально и только когда dependencies уже доступны или их установка предусмотрена текущим локальным workflow.

### 4.2 Livewire и Alpine.js

Проверить по фактическому способу подключения проекта:

- не загружается ли Alpine дважды (например, отдельно из `resources/js/app.js` и повторно в составе Livewire);
- не подключаются ли одновременно несовместимые варианты `@livewireScripts`, `@livewireScriptConfig` и ручного `Livewire.start()`;
- нет ли нескольких вызовов `Alpine.start()` / `Livewire.start()`;
- присутствуют ли Livewire assets на layout-страницах с компонентами;
- не потеряны ли directives `wire:click`, `wire:submit`, `wire:model`, `wire:loading`, `wire:key` при переносе HTML;
- совпадают ли методы, к которым обращаются `wire:click`/`wire:submit`, с методами соответствующих компонентов;
- не заменены ли рабочие Livewire-действия статическими HTML-кнопками из шаблона;
- нет ли JavaScript exceptions, после которых инициализация Livewire/Alpine прекращается.

Использовать ровно одну согласованную схему подключения Livewire/Alpine для установленной версии. Не копировать случайные решения с форумов без сопоставления с текущими версиями пакетов.

### 4.3 CSS и разметка

Проверить:

- не смешаны ли глобальные стили нового шаблона со стилями старого интерфейса;
- правильны ли порядок CSS imports и настройки Tailwind;
- не подключены ли две разные мажорные версии Tailwind либо одновременно Tailwind и Bootstrap, стили которых конфликтуют;
- не применяются ли глобальные селекторы `button`, `a`, `form`, `input`, `table`, `header`, `main`, `aside`, `*` к Livewire-компонентам без изоляции;
- не переопределены ли `display`, `position`, `overflow`, `pointer-events`, `z-index`, `height`, `width`, `box-sizing`, `font-size` и `line-height`;
- не нарушена ли вложенность/закрытие тегов при переносе HTML в Blade;
- нет ли вложенных `<button>`, кнопок внутри неожиданных форм, некорректных `<form>`, дублирующихся `id`;
- корректно ли работают breakpoints, sidebar, header, content container, таблицы, выпадающие меню и модальные окна.

Исправлять источник конфликта, а не компенсировать его десятками новых `!important`.

### 4.4 Кнопки, ссылки и формы

Для каждого действия проверить:

- предназначение элемента: навигация — `<a href>`, действие — `<button type="button">`, отправка формы — `<button type="submit">`;
- кнопки не имеют случайного `type="submit"`, если не должны отправлять форму;
- нет пустого `href`, `href="#"` без корректного поведения или `onclick`-заглушки;
- клик не перехватывается overlay, backdrop, невидимым элементом или `pointer-events: none`;
- нет постоянного `disabled`, блокировки через `wire:loading` или незавершённого loading-state;
- формы содержат правильные CSRF/Livewire механизмы и показывают ошибки валидации;
- маршруты, методы компонентов и серверные ответы соответствуют ожидаемому действию;
- после действия обновляются данные/состояние интерфейса и пользователь видит результат или ошибку.

Не считать кнопку исправленной только потому, что на неё можно нажать. Требуется проверить ожидаемый результат и отсутствие JavaScript/HTTP ошибок.

## 5. Проверка UI

Сначала установить список реально существующих страниц и компонентов. Не придумывать экраны, отсутствующие в проекте. Для каждой доступной страницы проверить:

1. Dashboard/главная после авторизации.
2. Sidebar, header, навигационные ссылки и пользовательское меню.
3. Списки клиентов и обращений: фильтры, поиск, сортировка, пагинация, если существуют.
4. Карточки записей: открыть, вернуться назад, перейти по связанным ссылкам.
5. Формы создания/редактирования: ввод, валидация, отправка, успешный результат.
6. Статусы и другие интерактивные элементы.
7. Dropdown, modal, toast/alert, confirm/cancel, если существуют.
8. Logout и поведение для неавторизованного пользователя.

Проверить минимум desktop и узкий viewport/mobile. Если доступен Browser/Playwright MCP в рабочем окружении, использовать его для фактического прогона страниц и кликов. Иначе выполнить доступные автоматические тесты и не заявлять, что ручной браузерный тест выполнен.

## 6. Порядок исправления

1. Составить краткую таблицу «симптом → подтверждённая причина → доказательство → минимальное исправление».
2. Выявить первопричину(ы), а не перечислять гипотезы как факты.
3. Исправить загрузку ассетов/двойную инициализацию/CSS/HTML/обработчики — в порядке, соответствующем установленной причине.
4. Сохранить новый внешний дизайн там, где это возможно; восстановить функциональность существующих компонентов и прежнее ожидаемое поведение.
5. Если причиной является ошибочное массовое преобразование Blade, откатить только повреждённые участки к последней рабочей версии, затем аккуратно применить необходимые изменения шаблона. Не откатывать несвязанные backend-файлы.
6. Не подменять работу по восстановлению фронтенда полной переделкой интерфейса.

## 7. Тестирование и критерии приёмки

Перед приёмкой:

- выполнить доступный локальный `npm run build`;
- выполнить `php artisan test` (или целевые feature-тесты, если полный набор не настроен);
- проверить доступные статические/линт-проверки, если они уже настроены;
- если требуется запустить браузерный тест, использовать установленный инструмент, не добавляя новую testing-платформу без необходимости;
- повторить проверки UI из раздела 5;
- проверить `git diff` и `git diff --check`;
- проверить, что не появились секреты, `.env`, логи с PII, `vendor/`, `node_modules/`, build-артефакты, которые не должны отслеживаться.

Считать задачу выполненной только если:

- в консоли нет новых необработанных JavaScript errors на проверенных страницах;
- CSS/JS загружаются успешно и соответствуют фактическому build manifest;
- все существующие ключевые кнопки выполняют свои реальные действия;
- формы успешно отправляются либо показывают штатные ошибки валидации;
- навигация, dropdown/modal (если есть) и состояние загрузки работают;
- разметка не перекрывает контент и проверена минимум на desktop и mobile-width;
- тесты и сборка имеют явно записанный результат;
- не изменены production, SWeb, `.env`, миграции и несвязанные бизнес-функции.

Если какие-либо пункты нельзя проверить из текущего окружения, указать их как непроверенные, а не объявлять исправленными.

## 8. Итоговый отчёт

В конце сообщить:

1. Фактическую рабочую директорию, ветку и исходный commit.
2. Какая версия фронтенда была до изменений и какая подключена сейчас.
3. Таблицу найденных причин: причина, доказательство (файл/строка, браузерная ошибка или тест), исправление.
4. Изменённые файлы и краткое описание изменений.
5. Результаты `npm run build`, `php artisan test` и браузерных проверок; команды и фактические результаты.
6. Какие кнопки/формы/страницы были проверены, что осталось непроверенным.
7. Итоговый `git diff --stat`, состояние Git и commit SHA, если создан commit.
8. Оставшиеся проблемы и понятный способ воспроизведения.
9. Подтверждение, что production и SWeb не изменялись.

## 9. STOP CONDITION

После точечного восстановления фронтенда, тестирования и отчёта остановиться. Не переходить к новым функциям, финансовому модулю, API расширениям, CI/CD или deployment.
